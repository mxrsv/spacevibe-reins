# Activity

Which Claude Code and Codex sessions are running now, what each one is doing, how it is titled, which commands keep failing, which tool call is open, and the one write: Stop, a SIGTERM to a pid that was looked up again from the live system. The Activity page reads one `ActivityReport` through `activity.read` and `activity.subscribe` ([core-protocol.md](core-protocol.md#activity-subscription) holds the wire shape and the poll). Terms follow [GLOSSARY.md](../../GLOSSARY.md).

## Where each fact comes from

| Fact | Read from |
| --- | --- |
| Claude session exists | `<claude root>/sessions/<pid>.json`: `pid`, `sessionId`, `procStart`, `status`, `name`, `nameSource`, `cwd`, `startedAt`; never the process table |
| Claude process alive | `kill(pid, 0)` (EPERM counts as alive), then `ps -o lstart=` against `procStart` |
| Claude transcript | `<claude root>/projects/<folder>/<sessionId>.jsonl`; subagent logs in `<sessionId>/subagents/` |
| Codex process | `ps -axo pid=,args=`; only the pid is kept, `args` is read to find the name and helper words |
| Codex thread | `lsof -nP -Fpn -p <pids>`: the open file `thread-writer-locks/<uuid>.lock` |
| Codex rollout | `<codex root>/sessions/**/rollout-…-<uuid>.jsonl` or `.jsonl.zst`; state from `task_started`, `task_complete`, `turn_aborted` |
| Title | Claude: `custom-title`, `ai-title`, status `name`, first prompt. Codex: `thread_name` in `<codex root>/session_index.jsonl`, first prompt |
| Running tool | The newest tool call in the log with no result yet: name, and as target the command, file path, description or pattern |
| Failed command | Claude: a `Bash` tool result with `is_error` and an `Exit code N` line. Codex: a `CommandExecution` item with a non-zero `exit_code`. Hook failures: Claude only |
| Last write | Modification time of the transcript or newest subagent log, not the status file's `statusUpdatedAt`, which goes stale |

## Runtime path

1. Every adapter lists its logs, then every adapter finds its live sessions in wire order: Claude Code lists the status files (`<digits>.json`) and checks each pid, then Codex asks the process adapter for the codex processes: one `ps`, then one `lsof` for those pids.
2. `Engine.Read` folds every live log (main transcript, at most 50 newest subagent logs, the rollout of each Codex lock) plus recent history, reading only bytes added since the last read.
3. Rows are built, sorted by CLI then newest write, and the failure and file lists are grouped from all folded logs.
4. A Claude row is `ended` when its process is gone (the row disappears 15 minutes after the last log write), `idle` for status `idle`, `running` for `shell`, `unmeasurable` for any other non-`busy` status, `waiting` for a `busy` turn with an open question tool, `unmeasurable` for a `busy` turn whose open tool call has had no log write for 30 s, else `running`. A Codex row exists only while its process lives and follows the rollout the same way, `idle` after `task_complete` or `turn_aborted`. A process whose rollout is missing, unreadable or whose thread is unknown is `unmeasurable` with its own reason code.
5. Stop takes `{cli, id}`, never a pid. It finds the process from the id ([Rules](#rules-that-are-easy-to-get-wrong)), reads its identity (`lstart` text and executable basename) once, reads it again right before the signal, sends SIGTERM, then polls `kill(pid, 0)` every 100 ms for up to 3 s and answers `exited`.

## Rules that are easy to get wrong

- **Claude rows come from status files, Codex rows from the process table, and nothing matches by name.** A Claude process with no status file has no row, and `Identity.Name` is only compared between two readings of one pid, never with `claude`. A Codex process matches when the first word of its `args` is `codex` or a path ending in `/codex`, unless a later whole word is `app-server` or `mcp-server`. Do not add detection by name elsewhere; add a vector to [parse_test.go](../../core/internal/proc/parse_test.go). See [codex.go](../../core/internal/proc/codex.go) `CodexPids`, [claude-sessions.go](../../core/internal/activity/claude-sessions.go), [codex-sessions.go](../../core/internal/activity/codex-sessions.go).
- **A Codex thread is bound to a process only through its open writer lock.** The rollout is found by the uuid ending its file name. Before the first prompt there is no lock: the row gets the id `pid:<n>:<start-ms>`, which binds it to that process start. When `lsof` fails the lock is unknown, so the row gets `pid:<n>:unknown`, and an empty `ThreadID` must not be read as "no thread yet" while `LockUnknown` is set. Child rollouts (`parent_thread_id` or `source.subagent` in `session_meta`) get no row. See [proc.Thread](../../core/internal/proc/codex.go), [codexProcessID](../../core/internal/activity/codex-sessions.go).
- **A visible row does not mean Stop will accept it.** The read path only needs `kill(pid, 0)` and drops a row to not-alive when `procStart` and `ps` disagree; a failed `ps` keeps it alive. Stop needs more: the status file's `procStart` must equal the live start (whitespace collapsed). Two start times that both parse and differ mean a reused pid (404). A missing, empty or unparsable start on either side is "cannot verify" (409), because the process may well be the session. The shell must keep both answers distinct. See `livePid` in [claude.go](../../core/internal/activity/claude.go) and [codex.go](../../core/internal/activity/codex.go).
- **A session's CLI picks its Stop lookup, and an id with no Activity adapter is an error.** Stop never looks a session of one CLI up as another CLI's (the old code looked every non-Codex id up in Claude Code's status files). `activity.stop` refuses any `cli` without the activity concept before that. See [stop.go](../../core/internal/activity/stop.go) `livePid`, [overview](overview.md#cli-registry-and-adapters).
- **Stop signals only a process it found and read twice itself.** The identity read with the pid and the one read just before `kill(2)` must be equal in start and name, otherwise nothing is sent (404; an unreadable second reading is 409). A pid out of range (`<= 0`, the `kill(0)` and `kill(-1)` cases) never reaches `kill`. Between the second reading and the signal a pid could still be reused; darwin has no way to close that window. Do not add a second caller of `Terminate` or a pid parameter. See [stop.go](../../core/internal/activity/stop.go), [validPid](../../core/internal/proc/adapter.go).
- **A title is the first candidate that is not junk, cut to 80 UTF-16 units.** Junk is a text under 2 units or with no letter or digit, a slash command, anything starting `<`, lifecycle and caveat text, or a placeholder such as `warmup` or `untitled`. A Claude status `name` is ignored when `nameSource` is `derived`. The first prompt is taken once and skips meta, compact-summary and sidechain records. With no candidate the title is `YYYY-MM-DD · <first 8 characters of the id>` (`unknown date` without a valid start; a thread-less Codex row shows `pid <n>` whole). Titles are the user's prompt text and are not masked. See [titles.go](../../core/internal/activity/titles.go).
- **Text helpers count UTF-16 units and use JavaScript whitespace on purpose.** The Node core wrote the goldens, and the cuts (title 80, failure title 120, preview 160, normalized command 400), the sort order and the white space set (U+FEFF is space, U+0085 is not) copy it. A cut inside a surrogate pair drops the half pair; invalid bytes become U+FFFD. The failure `key` is the sha of the 400-cut command, so another cut or space set changes keys and de-duplication, not only the display. Patterns ported from ICU use the sets in [icu-sets.go](../../core/internal/textjs/icu-sets.go) because RE2's `\s`, `.` and `$` differ. Do not use `len`, `strings.TrimSpace` or `strings.Fields` on log text. `textjs` is also imported by inventory, limits, mutate, rules, usage and roots, so a change is checked against every golden. See [doc.go](../../core/internal/textjs/doc.go), [icu-patterns.go](../../core/internal/activity/icu-patterns.go).
- **Credentials are masked where text becomes a report field, and never where a key is made.** The tool target is masked in `addPending`, before the 160-character cut; a failure title is masked before the 120-character cut; a failure `reason` is masked at the fold, before the 160-character cut (a command's error line in `errorLine`, a hook's first output line in `claudeHookFailure`), and once more when the group is built. The key, the hook hash and the de-duplication id come from the raw command. Not masked: `sessions[].title`, file paths, `stateReason`. A new field built from a command or output line goes through `redact.Command` before it is cut and before it leaves the core; never hash masked text. See [core-protocol.md](core-protocol.md#output-discipline-and-security-boundaries), [fold-common.go](../../core/internal/activity/fold-common.go), [groups.go](../../core/internal/activity/groups.go) `failureTitle`.
- **Logs are read from the tail with caps, so the lists are partial by design.** A first read of a live log starts at most 64 MiB before the end, any other log 4 MiB (the partial first line is dropped); a line over 16 MiB is skipped. A `.zst` rollout cannot seek: it is read whole, keeps the last lines up to the same cap, and is read again whole when its identity, size or mtime changes. A shrunk or replaced log is folded again from the start. History is the logs written in the last 14 days, newest 200, and the lists end at 200 failures and 300 files. A truncated log is counted in `stats.truncated` and gets no cost estimate. Do not present these lists as complete history. See [engine.go](../../core/internal/activity/engine.go), [tail-reader.go](../../core/internal/logs/tail-reader.go).

## Failure behavior

- **`ps` or `lsof` cannot start or runs too long.** Each run is a fixed argv with no shell, `TZ=UTC` and `LC_ALL=C`, stdin and stderr closed, killed after 3 s (one pid) or 5 s (a list) plus 0.5 s grace; stdout has no size cap. Absolute paths `/bin/ps` and `/usr/sbin/lsof`. A failed single-pid reading is unknown, never "no such process": Stop answers 409. A failed process list gives no Codex rows and one extra `codex-process-unknown` entry in `unmeasurable`; a failed `lsof` alone keeps the processes and marks each row `codex-process-unknown`.
- **A pid is reused between the read and Stop.** The start time differs: 404, nothing sent. Stop never retries.
- **The sessions folder.** Absent means nothing is running. Unreadable gives 409 from Stop, but the read path lists no Claude rows and reports no problem for it.
- **A log cannot be read.** A Claude row stays, built from its status file, with the cost note "exists but could not be read"; a Codex row becomes `unmeasurable` with `codex-rollout-unreadable`. The log adds nothing to the failure and file lists. A log that does not exist yields "No transcript found" or `codex-no-rollout`.
- **A session with no title** falls back as described above; it is never empty.
- **Not darwin.** The adapter reports not measurable: no Codex rows, every Claude process reads as not alive, and Stop answers 500 before looking anything up.

## Glance widget

The shell's floating widget ([spec](../specs/2026-11-19-session-glance-widget.md)) is a second reader of the same report, not a new source. Its countdown pill ([spec](../specs/2026-11-19-limit-reset-countdown.md), LC10) also reads `limits.read` every 60 s through the app's one `LimitsModel` ([GlanceLimitsFeed](../../Sources/SpaceVibe/Glance/GlanceLimitsFeed.swift)), so with the Limits page open there can be two reads a minute. [GlanceController](../../Sources/SpaceVibe/Glance/GlanceController.swift) owns it, and it starts only in a normal launch without `SPACEVIBE_TEST=1`.

- **A second subscriber, not a second poll.** [GlanceFeed](../../Sources/SpaceVibe/Glance/GlanceFeed.swift) opens its own `activity.subscribe` stream on the shell's one core connection. [CoreConnection](../../Sources/SpaceVibe/Core/CoreConnection.swift) sends `activity.unsubscribe` only after the last subscriber has left, plus its 1 s delay. So the core keeps polling while the widget is on, even with the Activity tab hidden or the main window closed, and turning the widget off in Settings ends the widget's subscription. A second subscribe resets the core's baseline and starts with a fresh snapshot, which the connection also gives the other subscriber (see [core-protocol.md](core-protocol.md#activity-subscription)).
- **The panels never become key.** The strip, the countdown pill, the hover list and the drag overlays are non-activating panels that refuse key and main. The widget therefore never takes typing focus from the front app. The cost is that a key press cannot reach it: Esc does not close the list (that needs a global key monitor and the Input Monitoring permission). A closed list is ordered out, so it never eats clicks.
- **Finding the host app starts no process (S-R4).** [HostAppResolver](../../Sources/SpaceVibe/Glance/HostAppResolver.swift) walks parent pids with `sysctl(KERN_PROC_PID)` in process and stops at the first pid that `NSRunningApplication` reports as a regular app. With no such ancestor (tmux, screen, ssh, a dead parent), the click opens Activity at that session through `ShellModel.openActivity(sessionItemID:)`. Do not replace the walk with `ps` or `Process`: S-R4 lists every process the app may start.
- **A press freezes the strip.** While the mouse button is down on the strip, re-renders are held ([GlanceRenderGate](../../Sources/SpaceVibe/Glance/GlanceDrag.swift)), because the panel replays the held press once it knows it was a click; a strip redrawn underneath would send the click to another session. While the pointer is over the strip, the pill or the list, the order inside each state group is frozen (`GlanceEntries.keepingOrder(of:)`) for the same reason.
- **A done session is a shell-side reading.** The core has no done state. [GlanceEntries](../../Sources/SpaceVibe/Glance/GlanceEntries.swift) shows `idle` with a log write in the last 10 minutes as done, and drops `ended` rows at once (the Activity page keeps them for 15 minutes).

## Verification

`cd core && SPACEVIBE_TEST=1 go test -count=1 ./internal/activity/... ./internal/proc/... ./internal/textjs/... ./internal/redact/...`. Every test builds its own home and fake process list; none reads the real `~/.claude` or `~/.codex` or signals a real process, except [stop_test.go](../../core/internal/activity/stop_test.go) `TestStopRealAdapter` and [system-darwin_test.go](../../core/internal/proc/system-darwin_test.go), which spawn and end their own child.

- Rows and lists against the frozen goldens: [golden_test.go](../../core/internal/activity/golden_test.go). Stop refusals and the reused pid: [stop_test.go](../../core/internal/activity/stop_test.go), [stop-verify_test.go](../../core/internal/activity/stop-verify_test.go). Masking before the cut: [redact_test.go](../../core/internal/activity/redact_test.go). ICU ports against recorded `NSRegularExpression` output: [icu-patterns_test.go](../../core/internal/activity/icu-patterns_test.go). `ps` and `lsof` parsing and the adapter: [parse_test.go](../../core/internal/proc/parse_test.go).
- Under `SPACEVIBE_TEST=1`, [proc.New](../../core/internal/proc/select.go) never returns the system adapter. With `SPACEVIBE_PROC_FIXTURE` it replays that file (`alive`, `starts`, `threads`, `delayMs`); without it, an empty list; an unreadable file is a startup sentence and an empty list. The fixture starts and signals nothing: `Terminate` only removes the pid from memory, and `Identify` answers `fixture-start` for a listed pid without a recorded start. So a Claude Stop succeeds only when the status file's `procStart` equals that pid's entry in `starts`; otherwise it is 409. A Codex row with a lock stops without either.
